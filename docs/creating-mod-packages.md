# Creating MOD packages

MODs extend Kokoro's UI and runtime. Unlike character packages, MODs may
contain executable JavaScript and HTML. Treat every MOD as untrusted code until
the user has reviewed its source, requested permissions, and capabilities.

## Package layout

The ZIP must contain `mod.json` at its root. A typical package looks like this:

```text
my-mod/
|-- mod.json
|-- LICENSE.md
|-- theme.json                       # optional
|-- layout.json                      # optional
|-- components/Panel.html            # optional registered component
|-- scripts/main.js                  # optional executable script
`-- assets/preview.webp              # optional supported media
```

The installer accepts HTML, JavaScript, CSS, JSON, PNG/JPEG/WebP/SVG/GIF,
fonts, TXT, and Markdown files. It rejects absolute paths, `..` traversal,
symlinks, corrupt archives, and unsupported extensions. The downloaded ZIP may
be at most 64 MiB; extraction also limits one file to 10 MiB and the unpacked
package to 50 MiB total. Keep referenced files inside the archive.

## Write `mod.json`

Required fields are `id`, `name`, `version`, and `description`. `id` may contain
letters, numbers, `_`, and `-`; `version` is semantic versioning. Add
`engine_version` whenever the MOD depends on a particular engine range. The
following is a complete minimal manifest with explicit optional fields:

```json
{
  "id": "my-mod",
  "name": "My MOD",
  "version": "0.1.0",
  "description": "A small interface enhancement.",
  "engine_version": ">=0.3.1, <0.4.0",
  "layout": "layout.json",
  "theme": "theme.json",
  "components": {
    "ChatPanel": "components/Panel.html"
  },
  "scripts": ["scripts/main.js"],
  "permissions": [],
  "capabilities": [],
  "entry": null,
  "ui_entry": null
}
```

All manifest paths are relative and use `/`. `components` maps a product slot
to an HTML file. `scripts` lists JavaScript entry points that run in the MOD
runtime. `entry` and `ui_entry` are legacy compatibility fields; leave them
`null` unless an existing MOD contract requires them.

## Request the smallest permission set

Allowed permissions are `tts`, `vision`, `memory`, `mcp`, `bot`,
`system.info`, `system.notifications`, `filesystem.read`, and
`clipboard.read`. Requesting a permission forces a review before installation.
Use `capabilities` to describe a narrower intent:

```json
{
  "capabilities": [
    {
      "name": "system.info",
      "risk": "read",
      "requires_confirmation": true
    }
  ]
}
```

Explain why each permission or capability is needed in the PR. Do not hide
network, filesystem, process, or credential access behind a generic name. The
runtime may reject unknown permissions or empty capability names.

## Security and trust

Checksum and HTTPS transport checks detect altered bytes; they do not make a
MOD safe. A registry entry can be `official` only when it came from the exact
canonical registry endpoint. A community mirror, local ZIP, or URL install
remains non-official. URL installation always shows an explicit untrusted-code
warning, even when the manifest requests no permissions.

Do not include secrets, private keys, credentials, or user data. Avoid writing
outside the MOD directory, and use Kokoro's provided APIs for events and
settings. License every source file and every third-party asset. A package
update is staged and reviewed before it replaces the previous MOD; a failed
validation must leave the previous version usable.

## Validate locally

Parse the manifest and run the existing Rust validators before creating a ZIP:

```bash
node -e "JSON.parse(require('fs').readFileSync('mods/my-mod/mod.json', 'utf8')); console.log('mod.json valid')"
cargo test --manifest-path src-tauri/Cargo.toml mods::manifest -- --nocapture
cargo test --manifest-path src-tauri/Cargo.toml commands::mods_registry_tests -- --nocapture
npm test -- scripts/build-content-registry.test.mjs
```

Test both a clean local install and an update over an older disposable copy.
Confirm that incompatible engine ranges, malformed manifests, traversal paths,
oversized archives, and unsupported files are rejected before extraction. Test
the requested permission confirmation and the URL warning. Record a real
result, owner, date, and evidence URL in the registry publication review. A
local test log is evidence for local validation only; it does not prove that a
GitHub raw URL or release upload exists.

## Submit a MOD

Use an immutable semantic version and generate the archive through the registry
builder. Include the manifest, source and license notices, compatibility range,
permissions/capabilities rationale, generated byte size, SHA-256, and install
or update smoke-test result in the pull request. Keep generated registry data
and the ZIP synchronized. Changing any executable code, manifest permission,
or bundled asset requires a new version and checksum.

The maintainer reviews the source, archive paths, permissions, compatibility,
and license terms before merging. A passing checksum is necessary for
publication but is never a substitute for reviewing executable code.
