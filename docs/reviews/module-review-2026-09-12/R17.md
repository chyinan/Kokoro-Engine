## 确认发现

### R17-F01 · P1 · 备份实际包含明文 provider 密钥，与 UI 的明确承诺相反

[CONFIG_FILES](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:36) 包含 llm/tts/stt/vision/imagegen/bot/telegram/MCP 配置。手动 [export_data](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2083) 和自动 [export_data_to_path](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2185) 直接写入完整配置文本，无密钥排除/脱敏。[LLM 配置](D:/Programs/Kokoro-Engine/src-tauri/src/llm/llm_config.rs:22) 与 TTS 配置存在持久化 api_key 字段。UI [BackupTab](D:/Programs/Kokoro-Engine/src/ui/widgets/settings/BackupTab.tsx:447) 展示 [zh 文案](D:/Programs/Kokoro-Engine/src/ui/locales/zh.json:1078)：“提供商凭据永远不会包含在备份中”；inspection 还 [恒定返回 false](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:1289)。

复现：只在临时 app-data 的 llm_config.json 写入假密钥 → 调真实 `export_data_to_path` → 解压 ZIP，`configs/llm_config.json` 含假密钥原文。新增 `review_r17_data_only_export_must_exclude_provider_credentials` 扫描所有 ZIP entry，断言假密钥不得出现，已实际失败并定位到上述 entry。没有读取/输出用户真实凭据。

影响：用户依据“不含凭据”说明分享或同步备份时会泄露可用 API key/token。手动和自动两条路径均受影响。修复建议：统一导出配置策略，排除 provider secrets、MCP env/header secrets、bot tokens；导入兼容旧含密钥备份时也应明确处理策略；检测值不得恒 false。用各配置族的假 sentinel 验证数据模式/资源模式/自动模式。

### R17-F02 · P1 · Skip 导入整数 ID 冲突会使提案/证据指向本库另一条记忆

[Skip memories SQL](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2553) 按原整数 id `INSERT OR IGNORE`，而 [依赖表导入](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2696) 随后对 candidates/evidence/jobs/proposals/operations 各自 `INSERT OR IGNORE ... SELECT *`。没有 memory_id/candidate_id/proposal_id 的统一映射，也没有因 parent 冲突而跳过其依赖。

复现：本库角色 A memory id=1；另一个备份中角色 B memory id=1 及本库尚不存在的 proposal id=20、target=1。选择 Skip：B memory 被跳过，B proposal 被插入并引用 A memory。R06-F02 的真实 MemoryManager 回归证明接着审批可覆盖 A；本次未把 SQL 复制测试当成完整 import_data 测试（入口绑定真实 AppHandle）。

另一可达触发：Overwrite 导入旧版没有 Dreaming 表的备份时，[仅在源表存在才删除旧依赖表](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2635)；memories 已全删全换，旧提案/证据却保留，原 id 可重新指向另一记忆。

修复建议：定义所有引用关系并统一重映射；若 Skip 明确保留本地冲突行，应连同不再有效的依赖一起拒绝/跳过，不可把外库引用自动接到本地。Overwrite 要清除相应旧依赖，再有条件恢复源表。恢复后执行角色/引用完整性检查，批准侧仍须独立约束归属。

### R17-F03 · P1 · 导出失败会先破坏目标位置已有备份

[create_regular_export_file](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:482) 使用 create+truncate，在任何源配置/DB读取和最终 ZIP 成功之前打开用户目标。随后遇非法 UTF8、超限文件、读取/磁盘错误会返回 Err，但原备份已被清空或替换为不完整 ZIP。

复现：已有 `existing.kokoro` → 让 app-data 某配置为非法 UTF8 → 导出覆盖同路径 → 返回错误后检查旧文件。新增 `review_r17_failed_export_must_preserve_previous_backup` 调真实导出，已观察到旧字节被新 ZIP 替代，保留断言失败；不使用真实用户目录。自动命名只有秒精度，也可能让并发任务碰撞同一路径。

修复建议：同目录独占临时文件完成 ZIP、flush/必要持久化及自检后原子替换；失败仅清理本次临时产物。自动文件名加入 UUID 或 create_new 并加进程内备份互斥。

### R17-F04 · P1 · 分别复制运行中的 SQLite 主库/WAL 不能构成一致快照

手动 [复制段](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2034) 与自动 [复制段](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2150) 先复制主 DB，再复制 WAL/SHM，然后对副本 checkpoint；没有 SQLite backup API、读快照事务或对写入/checkpoint 的统一锁。打开副本/checkpoint 的失败还被忽略。

具体失败时序：主库副本产生时，新提交仍在源 WAL；源随后 checkpoint 并截断 WAL；再复制 WAL 得到空/新一代 WAL。备份副本没有那批已提交数据，副本 checkpoint 不能重建已丢失的 WAL。此为实现级快照协议缺陷，未声称已做完整导出竞争复现；使用并发写+checkpoint 的真实导出回归仍开放。

修复建议：使用 SQLite online backup 或在受控连接上创建一致数据库快照，再归档该快照；所有校验/checkpoint错误显式传播，验收 `integrity_check`、事务序号和最后提交集合，而非仅 ZIP 可打开。

### R17-F05 · P2 · 导入并非完整 DB 恢复，摘要表遗漏且旧摘要可能残留

导出包含完整 kokoro.db；但 [导入事务](D:/Programs/Kokoro-Engine/src-tauri/src/commands/backup.rs:2564) 只恢复 memories、部分 Dreaming 表、conversations/messages 和 characters。`session_summaries`、`conversation_summaries`、`emotion_snapshots`、memory observability 表没有恢复逻辑。Overwrite 删除 conversations 时 `conversation_summaries` 按 FK cascade 被删除，又没有插回；`session_summaries` 没有 FK，旧库内容保留。`AIOrchestrator::compose_prompt` 会继续使用 session summary fallback。

复现：备份中含 ready conversation summary 和 session summary，在另一库 Overwrite 恢复。期望恢复对应上下文；实际新摘要缺失，旧同角色 session summary 可能继续进入提示词。静态确认；完整 GUI/IPC round-trip 尚未验证。

修复建议：建立版本化恢复表清单和引用次序；明确所有用户数据在 Skip/Overwrite 下的处理，对摘要/情绪/证据等做完整 round-trip 测试。可重建的观测统计可单独声明排除，但不要默默混用旧上下文。
