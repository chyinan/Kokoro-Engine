## 确认问题

### R05-001：迟到编辑响应覆盖新会话同位置消息（P1）

- 生产位置：`ChatPanel.tsx:2613–2707`，尤其 `:2662–2669`。
- 复现：A 显示 message 101→编辑并挂起 edit IPC→切到 B（message 201，文本 original B）→返回 A 的 `{message_id:101, updated_content:'edited in A'}`。
- 预期：B 的 201 / original B 保持不变，编辑仅归属 A。
- 实际：生产回调找不到 101 时回退 globalIndex，把 B 的消息文本和 ID 改成 A 的 101。渲染红测得到 `edited in AEdit`，预期包含 `original B`。
- 影响：跨会话文本及消息身份污染；后续编辑使用被替换的 ID，会被后端会话所有权校验拒绝。该复现没有证明 B 的数据库行被改写，后端现有校验阻止了这条直接写错数据库的路径。
- 相邻同因：`:2641` 等待 ID 时只取当前位置，`:2684` 失败恢复仍有位置 fallback，`:2699` 还可能用旧角色闭包触发新会话重同步。
- 最小修复：入口捕获 generation、conversationId 和 message identity；每次 await 后及状态更新前复核；成功/回滚只按原消息 ID 或 request ID 匹配，删除 globalIndex fallback；过期失败不向新会话写错误或发起 resync。
- 证据：`chat-edit-session-switch.test.tsx` 的 delayed edit 用例；报告证据文件如上。复核：已交总审，尚未修复或独立复核。

### R05-002：清空后仍携带旧会话 ID，下一轮被后端拒绝（P1）

- 生产位置：`ChatPanel.tsx:2556–2600` 清空消息但没同步 `activeConversationId` / ref；`:2365` 继续提交旧 ID。后端 `ai/context.rs:1793–1797` 将 current_conversation_id 清为 None；`commands/chat.rs:2208` 明确拒绝显式旧会话。
- 复现：加载 conv-A→清空确认→输入 first new message→提交。
- 预期：成功清空后发送不携带 conversation_id，后端创建新会话。
- 实际：新渲染测试捕获 `conversation_id='conv-A'`；与真实后端契约组合会返回 `Conversation changed while request was in-flight`。新请求不能恢复聊天，直到重新选择/新建会话或其他同步。
- 最小修复：clearHistory 成功后通过现有 `startEmptyConversation` owner 同步无会话状态及 UI；保留失败时原会话；捕获 generation 防止清空完成后的晚到回调清空后来切换的会话。回归保留“清空失败保留状态”和“清空后首轮成功”。
- 证据：同文件 clear-history 用例失败 `expected 'conv-A' to be undefined`；后端生产分支静态核验。复核：已交总审，尚未修复或独立复核。
