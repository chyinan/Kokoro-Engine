# R07 LLM providers 与 Codex runtime

审查日期：2026-09-12。范围：LlmService 配置与 provider 实例、OpenAI-compatible、Responses、Anthropic、Ollama、llama.cpp、消息/工具转换、Codex app-server JSONL 与子进程。仅审查代码及已有证据，没有读取凭据文件、调用真实 provider、启动 Codex runtime 或修改生产代码。

## 结论与验证边界

确认 3 项静态问题：provider 配置快照非原子、HTTP 流消费者取消不能立即停止后台读取、Codex 在返回 Stream 之前被取消时缺少清理 owner。其他协议差异列为明确测试缺口，没有因为文件大或缺测试自动判定有缺陷。

root 的 [Rust 基线](evidence/baseline-rust.json) / [原始日志](evidence/baseline-rust.log) 为 874 passed、0 failed；本次复查了 llm 的具体通过项。已覆盖配置正常切换、Responses 本地 HTTP/SSE、Anthropic 请求转换/模型列表、llama.cpp probe、Codex 纯协议转换等。没有新跑 Cargo；没有把 CLI 检测测试当作 app-server 生命周期测试。

## 现状与调用链

- `commands/llm.rs` 读取/保存配置、测试连接；保存调用 `LlmService::update_config`，先 normalize/build/persist，再更新内存字段。当前 provider、provider map 和完整 config 分属三把 RwLock。
- 聊天准备阶段取得 system provider，随后取得 chat provider；工具回合复用这个 chat provider Arc。已取得的 Arc 能固定该请求的实现对象，但不能修复取得 Arc 时的跨字段快照问题。
- OpenAIProvider 通过自有 reqwest HTTP/SSE 实现 rich history，保留 reasoning_content；Ollama/llama.cpp 使用共享 async-openai compatible helper。Responses 用 stateless request、原生 function output 和 provider data；Anthropic 转换为 Messages content blocks。
- HTTP streaming adapter 启动后台 task 读取上游，将事件放入 unbounded channel，返回 receiver；聊天层以 cancel/timeout 丢弃返回 Stream。
- Codex 创建独立临时 cwd、ephemeral/read-only thread，限制原生能力并把动态工具交回 Kokoro；维护 JSONL RPC pending、broadcast notifications、model/list 分页与 stream Drop interrupt。

## 发现

### R07-01 · P1 · 配置切换可产生混合版本快照并触发非用户选择的默认 provider

代码位置：`src-tauri/src/llm/service.rs:25`、`:109`、`:140`、`:152`、`:160`、`:441`；`src-tauri/src/commands/chat.rs:2192`、`:2395`。

update_config 按 providers → active_provider_id → config 的顺序分别获取锁并写入。try_provider 先读 active ID，再读 providers；system_provider 更分别读 config、active ID、map。没有统一快照或版本检查。

触发顺序：读请求取得旧 active ID A；配置更新将 map 切到只有 B 的版本；读请求在新 map 查 A 失败。`provider()` 把这个错误转换为 default_provider，而不是让调用者重试同一快照或明确失败。默认 provider 固定为 api.openai.com / gpt-4 / 空 key，不是原配置 A 或新配置 B。两个并发保存也可能在持久化和三段内存写之间交错。

影响：切 provider 的并发窗口可能得到错误端点/模型、配置错误或默认外部请求；不应把这里的 fallback 解释为用户授权的 provider 选择。system_model 还可能来自另一版本 config。静态调用链确认，未向任何端点发请求。

修复建议：用一个不可变状态快照统一包含 config、providers、active/system selections，并序列化保存提交；读请求一次获取快照。不存在可用 provider 时返回 typed error，不静默创建另一端点。现有“正常更新后再读取”单测需要补有 barrier 的并发读取/双保存测试。

### R07-02 · P2 · HTTP Stream 被取消后，上游读取 task 仍可持续等待

代码位置：`src-tauri/src/llm/provider.rs:215`、`:253`、`:571`、`:576`、`:635`；`src-tauri/src/llm/anthropic.rs:127`、`:132`、`:239`；`src-tauri/src/llm/responses.rs:91`、`:98`、`:288`。

各适配器返回 channel receiver，后台 task 的 handle 没有由 Stream 保存，也没有取消信号。task 只有再次从上游收到事件并尝试向已关闭 receiver 发送时才发现消费者已经取消。如果上游停在空闲 SSE、只发送不转发的事件，或者连接保持但无后续数据，消费者 drop 不会唤醒这个等待。

影响：聊天 UI 的取消/超时已经结束，但本地上游连接和远端推理可能继续，重复取消可留下多份等待任务。OpenAIProvider/Anthropic 创建的 reqwest client 也没有在本实现中设置流空闲超时；Responses/共享 SDK 是否另有内部限制需要单独验证，不能据此声称它们无限存活。

验证状态：static owner/drop 路径确认；没有运行真实服务或本地 SSE 压力测试。修复建议：让返回 Stream 持有读取 future 或 AbortHandle/cancel owner，drop 时停止 task 和 HTTP body；使用有界背压，区分 connect、first-output、idle、total deadline。用本地 SSE fixture 验证取消后不需等待下一个 delta 即关闭读取。

### R07-03 · P1 · Codex 在建立 Stream 前取消时，没有覆盖进程/turn/RPC 的清理 guard

代码位置：`src-tauri/src/commands/chat.rs:2796`；`src-tauri/src/llm/codex_runtime.rs:126`、`:193`、`:254`、`:411`、`:568`、`:643`、`:691`、`:702`。

chat 的 stream_creation_fut 外层有取消/连接超时 select，这会直接丢弃 `create_stream` future。CodexEventStream 的 Drop interrupt guard 直到 start_turn 完整返回后才创建。

两个未覆盖窗口：

1. app-server 已 spawn、stdout reader 已持有 server Arc，但 initialize 尚未完成。ensure_server 要等 `CodexAppServer::start` 返回后才把实例存入 `self.server/drop_server`。取消此 future 会跳过初始化失败分支的 shutdown，同时 provider Drop 尚不知道这个 server。`kill_on_drop(true)` 不能自动杀死仍被 reader Arc 持有的 child。
2. thread/turn 已开始、turn/start acknowledgement 尚未回来。取消跳过 request_with_timeout 的普通 error/timeout清理；没有创建 Stream guard，也没有发送 turn/interrupt。缓存 provider 可以继续持有 server，后台 turn 与 pending 请求未由此次取消处理。

影响：用户取消或聊天连接超时之后，启动中的 runtime/turn 可能继续，且反复尝试可能积累资源。已有 CodexEventStream Drop 对“成功返回 Stream 后”的取消有帮助，但不能覆盖前述两个窗口。

验证状态：从真实调用者的 select 到 provider 的 await/Drop 边界静态确认；未运行子进程复现。修复建议：从 spawn 开始建立可取消 owner，初始化/turn-start 期间丢弃 future 也必须 cleanup；未知 turn ID 时可销毁专用 server，或等 acknowledgement 后立即 interrupt；pending request 使用取消安全的 guard。不要仅依赖 future 正常返回 Err 的分支。
