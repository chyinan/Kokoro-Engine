## 发现

### R14-01 · P1 · 旧连接完成后重新注册已关闭、已删除或已替换的服务

代码位置：`src-tauri/src/commands/mcp.rs:77`、`:150`、`:210`；`src-tauri/src/lib.rs:682`；`src-tauri/src/mcp/manager.rs:159`、`:280`、`:295`。

这些后台任务在开始时 clone 配置，完成时直接按 name 插入 client，没有检查对应配置是否仍存在、仍启用、仍为同一次连接。manager 的 all_tools 遍历所有 clients，call_tool 也不检查配置 enabled。因此握手期间的关闭/删除不会使旧完成结果失效。

触发条件：服务处于 connecting 时关闭或删除；或用同名配置重新连接；旧握手之后才完成。结果可能复活已禁用服务，或由较晚完成的旧配置覆盖新配置。旧任务也能清除新任务的 connecting 状态。

影响：配置页面意图与实际可调用工具脱节，启动期和设置页均可发生。覆盖 client 没有负责关闭被替换连接，使生命周期问题进一步扩大。

验证状态：静态分支和消费者确认；未运行竞态复现。修复建议：服务记录持有 generation/config fingerprint/cancel owner；完成时 compare-and-insert，过期结果立即 shutdown；删除、禁用、替换统一使旧任务失效。注册目录只聚合当前有效、启用、连接成功的 client。启动入口也使用同一 owner。

### R14-02 · P1 · 所有 MCP 工具继承 Read + Safe，外部/写风险策略不起作用

代码位置：`src-tauri/src/mcp/bridge.rs:71`；`src-tauri/src/actions/registry.rs:142`、`:146`、`:199`；`src-tauri/src/actions/permission.rs:32`。

McpToolHandler 没有覆盖 `risk_tags()` 和 `permission_level()`，而 ActionHandler 默认值为 Read 和 Safe。make_action_info 直接复制这两个默认值，没有按 MCP 来源保守归类。MCP tool schema 在现有 bridge 只用来生成参数说明，不提供受信任的授权决策。

影响：用户将最大权限设为 safe 或屏蔽 external/write/sensitive 时，MCP 工具仍以 Read + Safe 参与判定。工具是否实际会写入或调用外部服务，不会反映到这个门禁。显式关闭某个工具仍有效，这不等于风险策略有效。

验证状态：静态元数据链确认；基线 `test_make_action_info_sets_default_metadata_for_mcp` 通过，仅说明当前默认行为被测试固定，不能证明默认值安全。没有执行权限演示。

修复建议：对未知 MCP 能力使用保守来源默认值，并设计明确的用户授权策略；服务器自报的描述/annotations 不能自行降低权限。列目录、prompt、执行与审计必须使用同一已确认元数据。

### R14-03 · P2 · 单个慢工具阻塞所有服务器状态与配置操作

代码位置：`src-tauri/src/mcp/bridge.rs:104`、`src-tauri/src/mcp/manager.rs:291`；`src-tauri/src/commands/mcp.rs:43`、`:107`。

McpToolHandler 获得全局 manager mutex 后，一直持有到网络工具返回。list/status、disconnect/remove、工具聚合及其他 server 的工具调用都需要同一把锁。现有“握手在锁外”的处理没有解决执行工具时的全局锁等待。

触发条件：任一服务器 tools/call 需要较长时间。影响：其他 server 的工具与设置页操作一起等待；用户想停止慢服务也先等待这个调用。不是必然死锁，当前传输超时可能最终释放锁。

验证状态：静态锁生命周期确认，未测时间曲线。修复建议：锁内取得当前 client 的 Arc 与 generation，立即释放 manager 锁；网络操作只持有必要的连接级状态；状态查询避免等待正在执行请求的 client 长锁。

### R14-04 · P2 · stdio 子进程 stderr 没有被消费

代码位置：`src-tauri/src/mcp/transport.rs:109`、`:112`、`:125`。

spawn 把 stderr 设为 piped，后续仅取出并消费 stdin/stdout。已读完整 spawn 路径没有 stderr reader。正常 MCP 服务若持续输出诊断信息，管道填满后其 stderr 写入会阻塞，随后请求可能超时。

验证状态：静态资源持有确认；未启动子进程或制造输出压力。修复建议：用有界、脱敏的 reader 消费 stderr，或在不需要采集时选择不会阻塞的合适重定向；reader 与连接 owner 同步结束。

### R14-05 · P2 · 失败握手及请求结束没有完整的资源回收所有权

代码位置：`src-tauri/src/mcp/manager.rs:378`、`:379`；`src-tauri/src/mcp/transport.rs:137`、`:149`、`:273`、`:305`、`:572`、`:652`、`:792`。

已确认的静态缺口：

- `build_connected_client` 在 `client.connect().await?` 失败时直接返回，没有显式 shutdown。stdio spawn 没有设置 kill_on_drop，关闭行为只在显式 shutdown 中杀直接 child；失败初始化的进程回收不能由该调用链保证。
- stdio pending map 在 reader/writer 内部；request 的 30 秒超时只丢弃 receiver，没有移除对应 pending 项。对保持连接但不响应的服务，多次超时会累积项，直到响应或 EOF/错误清理。
- SSE connect 启动的读取任务没有保存 JoinHandle/取消 owner；shutdown 只改标记并 drain pending。对不再发数据也不断开的 stream，等待中的读取是否及时结束没有保证。endpoint 等待超时也没有显式终止读取任务。

影响：重试与失联路径可能保留进程、连接、读取任务或 pending 项。Windows 经 cmd 启动的进程树是否整体回收也未验证；本报告不把“杀直接 child”表述为已保证清理所有后代。

验证状态：上述缺失路径静态确认；实际存活进程数、句柄数、pending 增量未动态测量。修复建议：使用连接级生命周期 owner，握手失败和替换结果均关闭资源；request 使用 drop/cancel-safe pending guard；SSE reader 有可唤醒的 shutdown；Windows 子进程树按同一 owner 清理。
