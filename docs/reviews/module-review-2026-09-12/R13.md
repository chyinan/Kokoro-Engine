## 发现

### R13-01 · P1 · 批准等待之后仍执行已禁用或策略已经改变的工具

代码位置：`src-tauri/src/commands/chat.rs:1592`、`:1600`、`:1623`、`:1714`、`:1789`。

`execute_single_tool_after_approval` 只读取最新 handler，不读取工具当前的 enabled 状态和权限策略，也不比较原批准对象与最新 action metadata。`ToolApprovalExecutionContext` 本身没有 ToolSettings，因此这个分支无法重验。正常初次执行在 `actions/executor.rs:1347` 和 `:1355` 做过的检查没有延续到批准后的最终副作用边界。

触发条件：一个工具因需要批准而暂停；等待期间用户关闭该工具，或将策略改为明确禁止；原批准请求随后得到批准。代码仍进入 handler。批准等待期间同 ID handler 被更新时，也会执行重新解析出的 handler，而非当时展示的版本。

影响：用户关闭工具或收紧策略后，仍可能发生旧请求的副作用。一次批准也可能应用到另一版 handler。用户批准应只豁免该次请求的可批准限制，不应豁免后来新增的 fail-closed 限制或关闭状态。

验证状态：静态调用链确认；未执行桌面交互复现。既有批准取消/晚到批准单测通过，但没有证明“批准等待期间禁用/策略变更/handler 替换”受到保护。

修复建议：把工具当前状态和稳定的执行身份带入批准续执行；在执行前重新检查 enabled、不可豁免的策略、registry generation 与批准对象。若请求或最终参数改变，使旧批准失效并重新形成可审阅请求。保持现有取消和总超时保护。

### R13-02 · P2 · Hook 的 success 字段只反映 Rust Result，忽略工具业务失败

代码位置：`src-tauri/src/actions/registry.rs:50`、`src-tauri/src/actions/executor.rs:1471`、`src-tauri/src/commands/actions.rs:450`、`src-tauri/src/commands/chat.rs:1634`。

`ActionResult::err` 返回一个 `success: false` 的结果值；例如 MCP 的 `isError` 在 `mcp/bridge.rs:110` 后转换为 `Ok(ActionResult::err(...))`。上述三个 AfterActionInvoke 调用处都用 `result.is_ok()` 生成 success，所以这个真实业务失败会被记录为 `success: true`。

影响：Hook 消费者和审计日志看到错误的执行状态。已有 payload 单测分别验证传入 true/false 的序列化，未覆盖实际调用者从 ActionResult 推导状态的行为。

验证状态：静态数据流确认；未增加或运行复现测试。建议在三条执行链共同使用业务结果判定：只有 `Ok(value)` 且 `value.success` 为真才记录成功，并保留失败消息。
