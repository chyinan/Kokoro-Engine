# R15 MOD 安装、UI/SDK 与 QuickJS 运行时

审查日期：2026-09-12。范围：MOD manifest/安装与更新、运行时与事件、mod:// 协议、iframe host proxy、SDK、组件注册、App 的 MOD action 分发。遵循 Registry AGENTS 的源绑定信任、安装权限确认、staging/path containment 与用户数据保留要求。

## 结论与证据边界

安装器已经有较完整的 archive/path/staging 校验。运行态边界存在 4 项静态问题：manifest 权限没有约束 host proxy，卸载未清除脚本监听与状态，脚本执行缺少可中断预算，旧请求结果可能发送给替换文档。安装成功不能作为运行时权限安全的证明。

复用 root 执行的 [Rust 基线](evidence/baseline-rust.json) / [日志](evidence/baseline-rust.log)：874 passed；[前端基线](evidence/baseline-frontend-scoped.json) / [日志](evidence/baseline-frontend-scoped.log)：72 文件、753 tests passed。没有新运行测试，没有修改生产代码。按最后范围指示，未运行的临时测试草稿已删除，不保留权限演示工具。

## 实际调用链与现有防护

- 安装/更新：`commands/mods.rs` inspect manifest → permission review → staging extract → 校验目录/既有包 → promote。Registry 安装还校验索引与包 metadata/permissions，URL 安装有 untrusted-code 确认。`commands/mods_registry_tests.rs` 对这些纯文件路径有基线通过记录。
- 展示：ModManager 发 theme/layout/components 事件 → 前端 ComponentRegistry/LayoutRenderer → IframeSandbox → 注入的 `public/mod-sdk.js`。
- iframe invoke：`IframeSandbox.tsx:203` 校验 source window → `:266` 全局 command allowlist → `:284` 通过宿主 Tauri invoke 转发。它没有用 manifest permissions 做调用者授权。
- iframe action：`:231` 接收 action → dispatch_mod_event 到 QuickJS，同时 `:246` 发 DOM 事件 → `App.tsx:1827` / `:1833` legacy 分发。这个通道不经过 invoke allowlist。
- QuickJS：`mods/manager.rs:182` 建立全局 runtime/context 与事件 relay → `load_mod` eval 脚本 → `mods/api.rs:50` 全局 listeners → DispatchEvent。`unload_mod:664` 清主题/布局并发出 UI unload。
- `mod://` 协议做路径 canonical containment，并设置 CSP/CORS；QuickJS 的 safe_join 会拒绝越过包根的路径。真实 WebView2 下的导航、origin 与协议策略未在本轮交互验证。

## 发现

### R15-01 · P1 · manifest 权限未限制宿主代理与配置副作用

代码位置：`src/ui/mods/IframeSandbox.tsx:75`、`:102`、`:116`、`:142`、`:231`、`:266`、`:284`；`src/ui/registry/ComponentRegistry.ts:43`；`src/ui/layout/LayoutRenderer.tsx:33`；`src/App.tsx:1872`、`:1906`、`:1917`；`src-tauri/src/commands/tool_settings.rs:22`。

permissions 被解构为 `_permissions`，没有参与判断。ComponentRegistry 与 LayoutRenderer 也传入空权限数组。全局 allowlist 包含 `save_tool_settings`、`delete_conversation`、`set_jailbreak_prompt` 等应用级操作，invoke 直接转发 iframe 提供的参数。Rust 的 save_tool_settings 是宿主设置命令，没有 MOD caller/grant 参数。于是具备已加载 iframe 的 MOD，无论声明的能力如何，都进入同一组宿主命令。

另一个 action 通道发 DOM 事件，App 的 legacy handler 处理 save_llm_config/save_vision_config/save_bot_config 等配置操作；单独缩小 invoke allowlist 无法覆盖此通道。

影响：安装确认展示的权限与运行时能做的事情不一致。对全局工具权限、对话删除、provider 或 Bot 配置的修改没有绑定 MOD 的授权身份。此结论不要求伪造其他窗口 source，也不主张 source 检查不存在；问题就在当前已注册 iframe 的权限边界内。

验证状态：静态入口、转发与消费者调用链确认；未构造或运行权限演示，未在 WebView2 验证外部页面能否加载。修复建议：基于已安装包身份与用户 grants，统一 host invoke、DOM action、QuickJS 能力授权；通用设置命令不直接暴露给 MOD。敏感副作用应在 Rust 边界再次验证 caller/grant，不能只依赖前端数组。

### R15-02 · P2 · 卸载 UI 后旧 MOD 的 QuickJS listeners 仍然存在

代码位置：`src-tauri/src/mods/api.rs:50`、`:67`；`src-tauri/src/mods/manager.rs:204`、`:233`、`:664`。

QuickJS context 在 manager.init 时创建，所有 MOD 脚本共用这个 context；Kokoro.on 将 callback 追加到全局 `__listeners`。unload_mod 只清 active_theme/active_layout、发 mod:unload 和 Hook，没有清 listeners、重建 context、终止脚本实例或给事件附加有效 MOD generation。重新加载脚本也会继续向同一 listeners 追加。

触发条件：正常 MOD 注册一个事件 callback，卸载后再发生同名 engine/action event；或 load → unload → load。代码仍可调到旧 callback，重载后可能重复执行。

影响：界面显示已卸载但旧脚本仍响应，多个 MOD 共享遗留状态；重复回调造成重复消息/动作。unload 的 Hook 还从 `loaded_mods.values().next()` 取 manifest，无法可靠表示实际活动 MOD。

验证状态：静态生命周期确认；未执行 QuickJS 复现。修复建议：用明确 active MOD instance/generation 管理 context、listeners 和 relay。卸载使该实例所有回调与待处理结果失效；加载新实例不能继承旧全局状态。为重载幂等性增加行为测试。

### R15-03 · P2 · 脚本执行没有可中断预算，挂起会占住 MOD manager

代码位置：`src-tauri/src/mods/manager.rs:190`、`:196`、`:227`、`:245`、`:510`；`src-tauri/src/commands/mods.rs:579`。

runtime/context 创建后直接 eval，没有执行截止时间或中断 handler。load_mod 等待 reply_rx 没有 timeout，且 commands/load_mod 在 await 期间持有 ModManager mutex。独立 QuickJS 线程能隔离部分工作，但不能让持锁的 load 调用结束。事件输出使用无界 std mpsc channel，也没有每实例流量预算。

影响：正常脚本缺陷导致长时间不返回时，load 无法完成，依赖同一 manager 锁的 list/unload 等操作也等待。大量脚本事件可能积压内存或日志。500ms health check 只检查初始化状态，不监控后续 eval。

验证状态：静态执行/锁/队列关系确认；未运行无限循环、事件压力或内存耗尽程序。修复建议：QuickJS interrupt budget、内存上限、事件有界队列与背压、连接级/实例级取消；不要在慢脚本执行期间持全局 manager 锁。只给 reply_rx 增加 timeout 不会停止仍运行的脚本，不能作为完整修复。

### R15-04 · P2 · 异步 invoke 的回复没有绑定发起文档

代码位置：`src/ui/mods/IframeSandbox.tsx:287`、`:289`、`:295`、`:313`。

Promise 完成时读取 `iframeRef.current.contentWindow` 与当前 `iframeOriginRef`，没有捕获并验证发起请求的文档/generation。effect 依赖 id，但不依赖 src。如果相同组件 id 的 src 替换或 iframe 导航，旧请求完成后会向当前文档发送旧结果。

影响：旧请求数据可能流向新组件文档；SDK 请求 ID 从页面本地计数开始，重载后的相同 ID 也可能误认旧回复。卸载整个组件后 ref 为空的情况会丢弃回复，这并不覆盖同组件换 src 的路径。

验证状态：静态闭包与依赖确认；未运行导航复现或 origin 演示。修复建议：为每次 src/document 实例生成会话标识；校验 ready origin/source 与预期来源；捕获发起 window/session，并在 resolve/reject 时验证仍匹配；替换或卸载时使旧调用失效。

## 修复复核（2026-09-12）

Iframe host invoke、DOM action 现在共同校验 manifest permission；高副作用命令默认移除，未映射 action fail closed，异步回复绑定 document/window/origin generation；QuickJS unload 清空 listeners。前端构建与 Vitest 通过，真实 WebView2 fixture 仍待安装版验证。

补充复核：`dispatch_mod_event` 已从 iframe invoke allowlist 移除，iframe 不能再把任意 action event 伪装成宿主命令绕过 action 权限门禁。真实 WebView2 恶意消息 fixture 仍待验证。

补充复核：LayoutRenderer 与 ComponentRegistry wrapper 现在通过 App 维护的 modId → manifest permissions 映射向 IframeSandbox 传递 host-approved grant，缺少映射时继续 fail closed。
