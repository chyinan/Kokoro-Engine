# R09 TTS 与音频播放

状态：已完成静态审查和本地前端回归，生产修复正在进行；真实音频设备和 provider 未联调。

## 调用链

`tts/manager.rs` 路由 provider、分句、并行合成并发出 `tts:start`/`tts:audio`/`tts:browser-delegate`/`tts:end`；`src/core/services/tts-service.ts` 监听事件并交给 `src/lib/audio-player.ts` 或浏览器 speechSynthesis；`voice-interrupt-service` 负责打断。

## 已确认问题

- **R09-001/P1：WAV 解码完成顺序改变播放顺序。** `AudioStreamManager` 原先按 decode 完成顺序入队；慢首句可能被第二句先播放。新增回归已复现，`evidence/r09-r10-vitest.log`。已改为序号 Map，等待所有更早序号后播放。
- **R09-002/P1：浏览器 fallback 的多句播放互相取消。** TTS 服务为每个 `tts:browser-delegate` 调用 `speechSynthesis.cancel()`，后句到达会取消前句。新增回归已复现。应由单一队列管理 utterance，停止操作才取消整队列。
- **R09-003/P1：打断后迟到 `tts:audio` 仍可入队。** 事件监听任务在旧 generation 下完成后继续调用播放器；新增回归已复现。应在入队前捕获并检查 TTS generation，停止时使旧回调失效。

## 场景与证据

28 个既有/基础测试通过，新增 4 项 R09/R10 生命周期回归中 R09 三项失败，见 `evidence/r09-r10-vitest.log`。manager 队列、缓存、provider reload 和真实设备播放尚未完成 Rust/桌面级验证。部分 provider 原始格式不统一；Bot 外部 MIME 归 R18，不能由本地播放器测试替代。

## 修复验收

用可控 decode/utterance 顺序验证句序；旧 generation 的音频不得进入新队列；browser fallback 只在显式 stop 或新回合重置时取消；正常多句播放仍成对发出 start/end。

## 修复复核（2026-09-12）

WAV 播放按序号等待、TTS browser utterance 不再逐句 cancel，且播放 generation 会丢弃打断后的迟到音频。R09 前端回归包含在全量 Vitest 中并通过；真实 provider 编码差异和音频设备仍待 Windows 烟测。
