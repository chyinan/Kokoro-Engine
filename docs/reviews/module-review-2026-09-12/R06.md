## 确认发现

### R06-F01 · P1 · 过期提案可恢复已删除记忆并覆盖之后的人工纠正

调用链：MemoryPanel 审批 → bridge `approveDreamProposal(id)` → `commands/memory.rs:201` → [approve_dream_proposal](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3803)。审批只检查提案仍为 pending；没有重新验证 source/target 的 active 状态、内容版本或 `updated_at`。随后 [UPDATE](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3837) 无条件写 content，并设置 `status = 'active'`。而用户删除实际为 [归档](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:2859)。

复现：创建 pending 提案 → 在记忆列表删除目标，或编辑成新的事实 → 再审批旧提案。预期旧提案失效并要求重新审查；实际归档会复活、人工修正被旧 `proposed_content` 替代。新增 `review_r06_approval_must_not_resurrect_deleted_memory` 与 `review_r06_approval_must_not_overwrite_newer_manual_edit` 直接覆盖两个操作序列，均已运行并按预期行为断言失败。

修复建议：提案记录来源版本/内容指纹；在提交事务内重新检查所有源仍属于同角色且 active、版本未变；缺失、删除或变更应将提案标记失效并明确返回冲突，禁止静默复活。

### R06-F02 · P1 · 提案的角色归属未约束目标和来源，导入冲突可跨角色写入

[加载提案来源](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3750) 仅按 memory id 查；审批 [目标更新](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3840) 和 [superseded 更新](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3863) 同样不检查 `character_id`。生成阶段的正常候选通常同角色，但 R17-F02 的 Skip/旧备份恢复能产生合法可到达的错指关系；不能依赖生成端的历史假设。

复现：本库角色 A 的 memory id=1；角色 B 的备份提案 target=1 经冲突导入保留。查看 B 的提案会读出 A 的来源内容，审批则覆盖 A。新增 `review_r06_proposal_must_not_modify_another_characters_memory` 用该导入后夹具调用真实审批，已经复现 A 的内容变为 proposal replacement；它不是完整 import_data 端到端测试。此发现与 R17-F02 是一条攻击/误操作链的两处根因，汇总时不应重复计算影响。

修复建议：读取提案时绑定显式 character id，事务内校验 target 和每个 source 的归属；管理 CRUD 也传递和验证所选角色。导入需同时建立全体关系 ID 的映射。

### R06-F03 · P1 · 审批多表写入不原子，失败后已改变记忆但提案仍待处理

[approve_dream_proposal](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3826) 从 embedding 开始后，目标更新、多个 source supersede、提案状态和 operation log 均单独 `.execute(&self.db)`。中间一步失败不会撤销之前已提交操作；状态检查也不在事务内，approve/reject 并发可覆盖最终决策。

复现：对 proposal 的 approved 更新设置 SQLite `RAISE(ABORT)` 故障触发器 → 调真实审批 → 返回错误，但 target content 已替换。新增 `review_r06_approval_failure_must_rollback_memory_changes` 已运行，故障错误被确认后，“失败保留原值”断言失败。自动合并 [auto_merge_dream_group](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:2987) 有同类逐条写入模式，需共享修复与回归。

修复建议：慢推理在事务外准备；事务内校验版本及 pending 状态，以条件更新领取提交权，更新 target/source/proposal/audit 后一次 commit。重复批准可幂等返回；已拒绝或过期不能转 approved。增加 approve/approve、approve/reject 和每个写入阶段故障测试。

### R06-F04 · P2 · MemoryPanel 切换角色后可被旧请求覆盖

[fetchDreaming](D:/Programs/Kokoro-Engine/src/ui/widgets/MemoryPanel.tsx:156) 与 [fetchMemories](D:/Programs/Kokoro-Engine/src/ui/widgets/MemoryPanel.tsx:215) 在请求结束后直接设置状态，没有请求序号、取消或当前角色检查。切角 effect 只重置页码/搜索；旧列表与提案也未随切角立即失效。

复现：延迟 A 的 listMemories/listDreamProposals，切 B 并先完成 B 请求，再完成 A 请求；下拉框仍为 B，内容及可点击的删除/审批 ID 已是 A。UI 允许用户以为自己正在修改 B。静态调用链确认；当前纯函数测试未覆盖此竞态，未做桌面复现。

修复建议：按 character+page+request generation 接受最新响应，切角色清除编辑/删除/审批状态，mutation 捕获明确角色并由后端复核。增加 deferred promise 的组件测试，包括 unmount 和两个轮询交叠。

### R06-F05 · P2 · 模型文件齐全但损坏时，“重试下载”直接返回 ready

[状态判断](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory_embedding_model.rs:94) 只看必需文件 `is_file()`；[下载入口](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory_embedding_model.rs:462) 遇 `status.installed` 立即返回，无模型验证。下载末尾验证失败后保留齐全文件，提示 retry；下次重试命中上述短路，无法修复，状态还能误报 ready。

复现：模型目录所有必需文件都存在，将 model.onnx 截断/损坏；调用状态/下载。静态确认；未修改用户模型，未执行真实 ONNX 复现。修复建议：区分存在、已验证、损坏；失败验证记录可修复状态，重试重新下载损坏集，完成态仅在成功加载后发布。用临时模型目录验证而非真实安装目录。

### R06-F06 · P2 · 重启前 pending/running 的摘要会永久阻止该会话再摘要

[get_conversation_summary_task](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:2440) 发现任何 pending/running 即返回 None，没有超时或恢复。初始化 [with_connect_options](D:/Programs/Kokoro-Engine/src-tauri/src/ai/context.rs:458) 只恢复 interrupted dream jobs；`conversation_summaries` 无对应恢复。后台 [provider.chat](D:/Programs/Kokoro-Engine/src-tauri/src/ai/context.rs:882) 又没有调用方超时。

复现：摘要标记 running 后退出进程/终止后台任务 → 重启并继续同会话。运行记录仍在，后续摘要一直被挡住。静态确认，尚无新自动测试。修复建议：启动时将孤立的 pending/running 转 interrupted/retryable，增加运行 lease/超时和重启回归；失败次数应跨重试累积，不能每建一条任务归零。

### R06-F07 · P2 · 自动合并改写内容但不更新 embedding 和 canonical_hash

LLM 自动合并可传 `assessment.merged_memory`，调用点 [memory.rs:3510](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3510)；[合并 UPDATE](D:/Programs/Kokoro-Engine/src-tauri/src/ai/memory.rs:3045) 写了新 content，却保留 keeper 原来的 embedding、canonical_hash 及结构化元信息。后续 semantic_search 使用旧向量，hash 去重仍按旧事实判断。

复现：让评估 provider 给出不同于 keeper 的合并事实并达到自动批准阈值 → 检查保存 content 与向量/hash。静态确认，尚无假 provider 回归。修复建议：按最终内容统一重建向量/hash/类型，跟 source 状态和审计原子提交；验收再次检索与重复写入的语义一致性。
